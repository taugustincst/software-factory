# Threat model — software-factory

Scope: the factory CLI, the agent pipeline (`factory run`), the dashboard, the scaffold templates, and the generated `factory.yml` workflow. Method: STRIDE per element, reviewed when a trust boundary, permission or data flow changes.

## System and trust boundaries

- **The agent runs code.** Pipeline stages execute an LLM agent (Claude Code) with write access to a working tree and a shell allow-list for build/test stages. Anything the agent reads — issue text, spec files, repo content — is untrusted input that can attempt prompt injection.
- **A dedicated API key.** CI runs use an `ANTHROPIC_API_KEY` repository secret that must be a dedicated, spend-capped key (its own workspace and monthly limit), never a personal or unbounded key. Local runs use the developer's Claude Code login instead; the factory itself never reads the key.
- **Guard hooks are a safety net, not a sandbox.** Hooks injected with `--settings` on every pipeline invocation parse commands with a shell tokenizer and block destructive commands, secret-like content and protected paths. Interpreter code (`node -e`, `python -c`) is not inspected; isolation comes from where the run executes.
- **Patch/ship split.** In `factory.yml` the agent job runs with read-only repository permissions, no persisted git credentials and no write token, and uploads the reviewed change as a patch. A separate `ship` job — which runs no agent — applies the patch and opens the PR with the write token.
- **The dashboard is local-only.** It binds 127.0.0.1, rejects foreign `Host` headers (DNS rebinding) and cross-origin POSTs (CSRF), and sends a strict CSP.
- **Run state is data, not code.** `.factory/runs/<id>/run.json` and logs are written atomically and read back by the dashboard and `factory ship`; run ids and log names are validated against strict patterns before any path is built from them.

## STRIDE

| Category               | Threat                                                                                                                  | Mitigations in place                                                                                                                                                                                                                                               | Residual risk                                                                                                          |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------- |
| Spoofing               | A non-collaborator labels an issue `factory` to spend the API budget or inject instructions.                            | `factory.yml` authorize job checks the actor's repository permission (admin/maintain/write) before any agent runs; only write-access users can apply labels. Local runs are started by the repo owner.                                                             | A compromised write-access account can trigger runs; the spend cap bounds the cost.                                    |
| Spoofing               | A fake run id or log name makes the dashboard/`ship` read or write outside `.factory/runs/`.                            | `RUN_ID_RE` / `LOG_NAME_RE` validation in `src/pipeline/store.js` before any path construction.                                                                                                                                                                    | Low.                                                                                                                   |
| Tampering              | Prompt injection in an issue/spec steers the agent to modify workflows, hooks or gates instead of the requested change. | Least-privilege tools per stage (spec/plan/review cannot edit code); gates re-run the project's own commands and re-read artifacts, so an agent claim cannot fake a pass; the review gate scans the diff for secrets/PHI; protected-path rules in the guard hooks. | A determined injection can still produce a plausible-looking malicious change — a human reviews every PR before merge. |
| Tampering              | The agent (or a dependency it installs) modifies the factory's own guard rules mid-run.                                 | Hooks are passed by absolute path from the installed factory package, not from the target repo; gates and patterns come from the package, and rule changes require tests in this repo.                                                                             | Runs executed from a modified local checkout inherit that checkout's rules.                                            |
| Repudiation            | "The agent did it" — no record of what a run did, spent or changed.                                                     | Every run persists `run.json` (stages, attempts, gate results, cost, branch, PR URL) plus per-attempt logs under `.factory/runs/<id>/`; CI uploads run artifacts; PRs carry the run id.                                                                            | Local runs deleted by the operator leave no record; acceptable for a local tool.                                       |
| Information disclosure | Secrets or real personal/PHI data are committed, logged or uploaded with run artifacts.                                 | Guard hooks block secret-like content; the review gate scans changed files for secrets and PHI patterns; gitleaks runs on every PR; agent logs are uploaded only for private repositories; test/demo data is synthetic by policy (`SECURITY.md`).                  | Pattern scanning cannot catch every secret shape; the dedicated, revocable API key limits blast radius.                |
| Information disclosure | The dashboard leaks run data to a website the developer visits (DNS rebinding / CSRF).                                  | 127.0.0.1 binding only, Host header check, Origin check on POST, strict CSP, no `innerHTML`.                                                                                                                                                                       | A local process can still read `.factory/` from disk; that is the operator's own machine boundary.                     |
| Denial of service      | A runaway run spends unbounded API budget or loops forever.                                                             | Per-stage spend caps, `--max-run-usd` run cap (default $15), per-stage attempt limits, review-loop limit, cooperative cancellation (Ctrl-C/SIGTERM, dashboard cancel), and the dedicated key's workspace monthly limit in CI.                                      | A run can still spend up to its caps before stopping.                                                                  |
| Denial of service      | Concurrent runs corrupt each other's state in one repo.                                                                 | A per-repo run lock (`src/pipeline/lock.js`); the dashboard refuses to start a second run in a locked repo.                                                                                                                                                        | Two factories pointed at one repo from different machines are not coordinated.                                         |
| Elevation of privilege | The agent job's token is used to push code or approve its own PR.                                                       | The agent job has read-only permissions, `persist-credentials: false` and no write token; the ship job holds the write token and runs no agent; branch protection on `main` requires code-owner review and CI.                                                     | If branch protection is disabled in a generated repo, a merged PR is the operator's decision, not a control failure.   |
| Elevation of privilege | A scaffolded project's install step runs arbitrary code on the developer's machine.                                     | Templates are first-party and pinned: generated CI installs the factory from an immutable commit (`FACTORY_PACKAGE`); post-scaffold install runs the template's own declared command and is skippable with `--no-install`.                                         | Any `npm install` executes dependency lifecycle scripts; that is the ecosystem's standing risk.                        |

## Review triggers

Revisit this model when: a new executor or tool is added to a stage; workflow permissions change; the dashboard gains a non-local mode; run records start containing new data classes; or a new template adds a data store or an external integration.
